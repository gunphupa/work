# การเก็บข้อมูลประเมิน ReBuild จากการใช้งานจริง

หน้า `/#/research` เป็นแบบบันทึกการประเมินต้นแบบ ไม่ใช่ผลวิจัยสำเร็จรูป ไม่มีการสร้างผลผู้เข้าร่วมขึ้นมาเอง และไม่ได้ส่งข้อมูลวิจัยเข้าเซิร์ฟเวอร์ ผู้เข้าร่วมต้องยินยอมก่อนเริ่มบันทึกและส่งออกไฟล์เอง

## ก่อนเริ่มเก็บข้อมูล

1. ผู้วิจัย/ครูที่ปรึกษาทบทวนวัตถุประสงค์ เกณฑ์สำเร็จ และวิธีขอความยินยอมให้เหมาะกับกลุ่มผู้เข้าร่วม รวมถึงข้อกำหนดของโรงเรียนหากผู้เข้าร่วมเป็นผู้เยาว์ การยินยอมในหน้าเว็บเป็นเพียงส่วนของเครื่องมือ ไม่ทดแทนกระบวนการที่โรงเรียนกำหนด
2. ตรึงรุ่นเว็บไซต์ก่อนรอบหลัก เปิด `/api/health` เก็บค่า `release` และใช้รุ่นเดียวกันตลอดการเก็บข้อมูล หากจำเป็นต้องแก้บั๊ก ให้จดว่าใครใช้รุ่นใด แยกวิเคราะห์เมื่อการเปลี่ยนแปลงกระทบภารกิจ
3. ทดลองนำร่องก่อนด้วยรหัสเฉพาะ เช่น P901 และเลือก `นำร่อง` ห้ามนำมาปะปนกับรอบหลักโดยไม่รายงาน
4. กำหนดรหัสจริงไม่ซ้ำให้ผู้เข้าร่วม เช่น P01–P20 หากมีผู้เข้าร่วมจริง 20 คน อย่าใส่ชื่อจริง/อีเมลในตัวเครื่องมือ เก็บรายการจับคู่รหัสกับบุคคลแยกต่างหากเฉพาะเมื่อจำเป็น
5. ให้ทุกคนใช้โจทย์ วัสดุ เงื่อนไขช่วยเหลือ และเกณฑ์ประเมินที่เทียบกันได้ บันทึกอุปกรณ์/เครือข่ายแยกในแบบวิจัยหากต้องใช้วิเคราะห์ หน้าเว็บนี้ไม่ได้เก็บตัวระบุอุปกรณ์อัตโนมัติ

## ขั้นตอนของผู้เข้าร่วมแต่ละคน

1. เปิดหน้า **บันทึกการทดสอบ** อ่านคำอธิบาย ใส่รหัส เลือกนำร่อง/รอบหลัก แล้วกดยินยอม หากไม่ยินยอม เว็บไซต์ส่วนอื่นยังใช้งานได้ตามปกติ
2. เลือกภารกิจและกด **เริ่มจับเวลาภารกิจ** แถบสถานะจะติดตามไปหน้าอื่นด้วย
3. ทำภารกิจจริง กลับไปหน้าบันทึก แล้วกด **หยุดจับเวลาเมื่อทำภารกิจจบ** ทันที ตัวเลขเวลาจะหยุดก่อนกรอกผล จึงไม่นับเวลาเขียนคำอธิบายผลเพิ่มเติม
4. เลือกผลตามที่สังเกตจริง กรอกจำนวนครั้งที่ได้รับความช่วยเหลือ/ข้อผิดพลาด และบันทึกสิ่งที่เกิดขึ้น ผู้วิจัยควรกำหนดล่วงหน้าว่าอะไรนับเป็นข้อผิดพลาดหรือการช่วยหนึ่งครั้ง
5. ทำอีกสามภารกิจ กรอกความคิดเห็นหลังใช้ แล้วกด **จบการทดสอบและหยุดบันทึก** เหตุการณ์ใหม่จะไม่ถูกเพิ่มเข้า session นั้น
6. ส่งออก **JSON** เพื่อรวมข้อมูล และ **CSV** เพื่ออ่านตาราง ให้ผู้วิจัยด้วยช่องทางที่ตกลงกัน ผู้เข้าร่วมสามารถถอนตัว/ลบข้อมูลในเครื่องได้ แต่การลบในเบราว์เซอร์ไม่ลบไฟล์ที่ส่งออกหรือส่งไปแล้ว ต้องแจ้งผู้วิจัยให้จัดการไฟล์เหล่านั้นด้วย

## ภารกิจและเกณฑ์ตัวอย่างที่ใช้ในเครื่องมือ

| ภารกิจ                | หลักฐานที่ผู้สังเกตควรตรวจ                                                     |
| --------------------- | ------------------------------------------------------------------------------ |
| ค้นหาและเลือกโปรเจกต์ | เลือกโปรเจกต์หนึ่งงาน เปิดแหล่งต้นฉบับ และอธิบายความเหมาะสมกับวัสดุได้         |
| ระบุวัสดุที่ขาด       | บอกของที่ขาดและจุดที่ต้องตรวจขนาด/สเปก/จำนวน ไม่เหมารวมวัสดุชื่อคล้ายกัน       |
| อธิบายขั้นตอน         | อธิบายลำดับหลักด้วยคำตนเองและข้อควรระวังที่มีในคู่มือ ผู้สังเกตเทียบกับต้นฉบับ |
| บันทึกและเปิดแผน      | บันทึกแผน ออกไปหน้าอื่น เปิดแผนเดิม และตรวจว่าขั้นตอน/บันทึกยังอยู่            |

ผลสำเร็จเป็นผลที่ผู้สังเกตหรือผู้ทดลองกรอก ระบบไม่ได้อ่านใจหรือยืนยันว่าผู้ใช้เข้าใจจริงอัตโนมัติ ภารกิจเหล่านี้ยังไม่พิสูจน์ว่าสร้างชิ้นงานจริงได้หรือช่วยลดปริมาณขยะ ต้องใช้การทดลองคนละแบบหากต้องการสรุปผลเหล่านั้น

## เวลาและขอบเขตการบันทึก

- ตัวจับเวลารวมเวลาที่อยู่หน้าอื่น ระหว่าง runtime เดียวกันใช้ monotonic clock เพื่อลดผลจากการปรับนาฬิกาเครื่อง เมื่อรีโหลดหรือไปควบคุมในอีกแท็บจะใช้เวลาจากนาฬิกาเครื่อง และส่งออก `timing_basis=wall_clock` ให้ตรวจแยกได้ อย่าเปลี่ยนนาฬิการะหว่างทดสอบ
- การกรอกผลหลังหยุดเวลาไม่เพิ่มเวลาภารกิจ ตัวจับเวลาที่ทิ้งหรือยังไม่บันทึกผลไม่ถูกนับเป็นภารกิจสำเร็จหรือไม่สำเร็จ
- เหตุการณ์อัตโนมัติเก็บเฉพาะชื่อเหตุการณ์ เวลา จำนวนผล และสถานะที่รองรับ ไม่เก็บ prompt รูปภาพ ชื่อวัสดุ หรือข้อมูลบัญชีในบันทึกวิจัย
- การค้นหาที่เริ่มก่อนยินยอมหรือเสร็จหลัง session เดิมจบจะไม่ถูกโยกไปใส่ session คนถัดไป
- ความเห็นอิสระอาจมีข้อมูลที่ผู้ใช้พิมพ์เอง ควรย้ำไม่ให้ใส่ข้อมูลส่วนตัวและตรวจไฟล์ก่อนเผยแพร่
- ข้อมูลอยู่ในเบราว์เซอร์นี้เท่านั้น ไม่ซิงก์ไป Supabase และไม่ได้ถูกสำรองโดย Render persistent disk การล้างข้อมูลเบราว์เซอร์จะลบข้อมูลนี้ จึงควรส่งออกทุกครั้ง
- จำกัด 50 sessions, 40 ภารกิจ และ 200 เหตุการณ์ต่อ session รวมขนาด 1 MB เมื่อเต็มจะไม่ทิ้งข้อมูลเก่าเงียบ ๆ ให้ส่งออกก่อนลบ
- แบบคะแนน 1–5 เรื่องประโยชน์ ความชัดเจน และความง่ายเป็นแบบที่ผู้พัฒนาออกแบบเอง **ไม่ใช่ SUS หรือแบบวัดมาตรฐานที่ผ่านการตรวจสอบ** หากรายงานเป็นงานวิจัยควรให้ครูทบทวนเครื่องมือก่อน

## รวมผลหลายคนด้วยสคริปต์

จากโฟลเดอร์โค้ดที่ติดตั้ง dependencies แล้ว:

```bash
npx tsx scripts/analyze-research.ts --out /tmp/rebuild-study-summary /path/to/P01.json /path/to/P02.json
```

ใช้โฟลเดอร์ output ที่ยังไม่มี สคริปต์จะไม่เขียนทับการวิเคราะห์เก่า รองรับไม่เกิน 200 ไฟล์และ 50 sessions ที่ไม่ซ้ำต่อชุด ถ้ามี snapshot ซ้ำของ session เดียวกัน จะใช้ประวัติที่ยาวกว่าซึ่งเข้ากันได้ ถ้าข้อมูลขัดแย้งจะหยุดและบอก session ที่ต้องตรวจ ไม่เลือกผลที่ดูดีกว่าเอง

ไฟล์ที่ได้:

- `combined-research.json`: ข้อมูลที่รวมและตัด session UUID ซ้ำ ไม่เติมผลที่ขาด
- `observations.csv`: ข้อมูลรายภารกิจ เหตุการณ์ และความคิดเห็น ป้องกัน spreadsheet formula จากข้อความผู้ใช้
- `task-summary.csv`: แยกนำร่อง/รอบหลักและแยกชนิดภารกิจ แสดงจำนวนครั้ง สำเร็จ/ไม่สำเร็จ/หยุดทำ อัตราสำเร็จ เวลาเฉลี่ย/มัธยฐาน/ต่ำสุด/สูงสุด และจำนวนความช่วยเหลือ/ข้อผิดพลาด
- `analysis-notes.txt`: ข้อจำกัดและรหัสที่มีหลาย sessions ให้ผู้วิจัยตรวจว่าทำซ้ำโดยตั้งใจหรือเป็นคนละคนใช้รหัสผิด

ทุก attempt ที่บันทึกถูกนับ รวมการทำซ้ำ ต้องกำหนดเกณฑ์ว่าจะวิเคราะห์ครั้งแรก ทุกครั้ง หรือครั้งอื่นไว้ก่อน ไม่ควรตัดผลที่ไม่ดีออกภายหลังเพียงเพื่อให้คะแนนสูงขึ้น รหัสผู้เข้าร่วมไม่ใช่หลักฐานยืนยันจำนวนคนจริง และกลุ่มเพื่อนเป็นกลุ่มตัวอย่างตามสะดวก ไม่ได้แทนผู้ใช้ทั้งหมด

## สิ่งที่ผู้วิจัยยังต้องทำเอง

ขอความยินยอมตามบริบทจริง จัดหาผู้ทดลองจริง แจกโจทย์และรหัส สังเกต/ตรวจคำตอบจริง รวบรวมไฟล์ ตรวจความครบถ้วน ตกลงเกณฑ์วิเคราะห์กับครู และเขียนข้อสรุปตามผลที่เกิดขึ้น เครื่องมือช่วยบันทึกและคำนวณ ไม่สามารถทำขั้นตอนเหล่านี้แทนคนจริงได้
