# ReBuild: ระบบค้นหา แผนงาน และการเก็บข้อมูลวิจัย

คู่มือนี้อธิบายสิ่งที่เพิ่มจริง ข้อจำกัด และขั้นตอนที่เจ้าของบัญชีต้องทำ ไม่ใช่ผลประเมินจากผู้เข้าร่วมวิจัย

## สิ่งที่เพิ่มและวิธีใช้

1. **ค้นหาจากอินเทอร์เน็ต** — ไป `#/web-projects` เลือกวัสดุหรือพิมพ์สิ่งที่มี เลือกระดับความยาก เวลา งบประมาณ และต้องการหลีกเลี่ยงการซื้อเพิ่มได้ เงื่อนไขเป็นคำขอในการค้นหา ไม่ใช่การรับประกันราคา/เวลา/ความพร้อมของวัสดุ
2. **กลับมาทำต่อ** — ร่างคำค้นและตัวเลือกเก็บในแท็บเดิม ผลซ้ำที่ตรงกันภายในเซสชันและช่วง cache จะไม่เรียก AI ใหม่ วันที่แสดงยังเป็นวันที่ค้นจริงเดิม
3. **ดูระยะเวลารอ** — แสดงเวลาที่ผ่านไปจริง ยกเลิกได้ ไม่มีเปอร์เซ็นต์หรือขั้นตอนที่เดาว่าเซิร์ฟเวอร์ทำเสร็จแล้ว
4. **ตรวจวัสดุ** — แสดงของที่อาจตรงกัน สิ่งที่ขาด และข้อที่ต้องตรวจจำนวน/ขนาด/สภาพ จำนวนที่ต้นฉบับไม่ระบุยังคงเป็นไม่ทราบ ไม่มีการคัดลอกจำนวนในคลังไปเป็นจำนวนที่คู่มือต้องใช้ แยกการถอดรายการจากต้นฉบับออกจากขั้นจับคู่คลัง โดยโค้ดประกอบรายการวัสดุและขั้นตอนจากผลถอดข้อมูลเดิม ขั้นจับคู่เพิ่มคำแนะนำทดแทนได้ในส่วนแยก แต่เพิ่มวัสดุหรือขั้นตอนที่อ้างว่าเป็นของต้นฉบับไม่ได้ ทั้งนี้การถอดข้อมูลยังใช้ AI จึงยังต้องตรวจหน้าต้นฉบับ
5. **บันทึกโปรเจกต์ภายนอก** — กดบันทึกแผน แล้วเปิด “งานที่บันทึก” (`#/builds`) แผนเก็บสำเนาคู่มือ แหล่งอ้างอิง เวลาค้นและวัสดุที่ใช้ค้นในเบราว์เซอร์ อ่านได้โดยไม่ต้องค้นใหม่
6. **ติดตามงาน** — เช็กขั้นตอนที่เสร็จ วัสดุที่เตรียมแล้ว จดบันทึก นำเข้า/ส่งออกแผน พิมพ์หรือเลือก Save as PDF จากหน้าต่างพิมพ์ของเบราว์เซอร์ นำเข้าจะไม่ทับความคืบหน้าของแผนที่มีอยู่
7. **ถามต่อจากแผน** — เปิดแผนที่บันทึกแล้วพิมพ์คำถาม AI จะได้รับคำถามกับข้อมูลแผน ไม่ได้ค้นเว็บเพิ่มในโหมดนี้ คำตอบไม่เปลี่ยนจำนวนวัสดุหรือแผนให้อัตโนมัติ ใช้โควตาและเครดิต AI เดิม
8. **ให้ข้อเสนอแนะ** — เลือกมีประโยชน์/วัสดุไม่ตรง/ลิงก์เสีย พร้อมข้อความเพิ่มเติม ข้อเสนอแนะเก็บในเบราว์เซอร์ ดาวน์โหลดหรือลบได้ ไม่ถูกโพสต์สาธารณะ
9. **คลังวัสดุ** — กรองสภาพและประเภท เรียงชื่อ/จำนวน ระบุที่เก็บส่วนตัว เลือกหน่วยสำหรับของที่เพิ่มเอง ค้นชื่อไทย อังกฤษ ชื่อเรียก และที่เก็บได้
10. **ใช้วัสดุแล้ว** — กด “บันทึกการใช้วัสดุ” ระบุจำนวนและยืนยัน ระบบลดจำนวนหรือเอารายการออกเมื่อใช้หมด การเลือกหรือบันทึกโปรเจกต์อย่างเดียวไม่หักของ
11. **สำรองข้ามเครื่องแบบเลือกเอง** — ในหน้าบัญชี กดตรวจข้อมูลสำรองก่อนอัปโหลด/คืนค่า มีการตรวจรุ่นข้อมูลป้องกันทับข้อมูลที่เพิ่งเปลี่ยนจากเครื่องอื่น ต้องตั้งค่า SQL ก่อนตามหัวข้อถัดไป ไม่มีการซิงก์อัตโนมัติ
12. **บันทึกการทดลองวิจัย** — `#/research` ขอความยินยอม ใช้รหัสผู้เข้าร่วม แยกรอบนำร่อง/รอบหลัก จับเวลาและบันทึกผลภารกิจ ส่งออก JSON/CSV และลบได้ ไม่มีการส่งให้ผู้วิจัยอัตโนมัติ

ขั้นตอนแจกโจทย์ รวมไฟล์หลายคน และคำสั่งวิเคราะห์อยู่ใน [`RESEARCH_COLLECTION.md`](RESEARCH_COLLECTION.md) เครื่องมือรวมไฟล์ใช้ `scripts/analyze-research.ts` จะไม่เติมผู้เข้าร่วมหรือผลที่ขาดให้เอง

การระบุภาพหลายภาพ การตรวจชื่อก่อนเพิ่ม การเพิ่มของเอง การรวมรายการซ้ำที่ผู้ใช้ยืนยัน คำแนะนำวัสดุทดแทนในคู่มือ บัญชี Google/อีเมล และคิวตรวจรีวิวเป็นฟังก์ชันเดิมที่ยังอยู่ ไม่มีการซื้อบริการหรือเปลี่ยนแพ็กเกจเพิ่มในงานนี้

## ข้อมูลอยู่ที่ไหน

| ข้อมูล | ที่เก็บ/วิธีนำออก |
| --- | --- |
| คลัง รูปประกอบรายการ ที่เก็บของ งานจากคู่มือเดิม | localStorage; สำรองที่หน้าคลัง หรือเลือกอัปโหลดบัญชีหลังตั้งค่า |
| แผนภายนอก ขั้นตอน บันทึก รายการที่เตรียม | localStorage แยก สูงสุด 50 แผน/2 MB; ส่งออกที่งานที่บันทึก |
| คำค้นและตัวเลือกที่ยังทำต่อ | sessionStorage ในแท็บนั้น ไม่ใช่ข้อมูลสำรองถาวร |
| ข้อเสนอแนะผลค้นหา | localStorage; ส่งออก/ลบที่หน้าค้นเว็บ |
| ผลวิจัยและความยินยอม | localStorage แยก; ส่งออก/ถอน/ลบที่หน้าบันทึกการทดลอง |
| cache ผลค้นหา | หน่วยความจำเซิร์ฟเวอร์ แยกตามเซสชัน จำกัดขนาดและอายุ รีสตาร์ตแล้วหาย |
| โควตา เซสชัน และสถิติระบบแบบรวม | SQLite ที่ `QUOTA_DB`; ต้องอยู่ใน persistent disk |
| ความคิดเห็นสาธารณะและบัญชี | Supabase ตามระบบเดิม |

การสำรองผ่านบัญชี **รวมรูป บันทึก และที่เก็บของในคลัง** เมื่อผู้ใช้กดยินยอมอัปโหลด แต่ไม่รวมแผนภายนอกหรือผลวิจัย การค้นเว็บไม่ส่งรูปส่วนตัว บันทึก หรือที่เก็บของ การอ่านรูปด้วย AI เป็นการส่งภาพที่ผู้ใช้เลือกและยินยอมแยกต่างหาก

## เจ้าของต้องทำ: เปิดสำรองผ่านบัญชี

1. เปิด Supabase โปรเจกต์ ReBuild → SQL Editor
2. คัดลอกทั้งไฟล์ [`supabase/private-backups.sql`](../supabase/private-backups.sql) ลง query ใหม่แล้ว Run ไม่ต้องแก้คีย์ในโค้ด
3. ทดสอบเข้าสู่ระบบบัญชี A → บัญชี → ตรวจข้อมูลสำรอง → อัปโหลดชุดข้อมูลเล็กที่ยินยอมให้สำรอง
4. เปิดอีกเบราว์เซอร์ด้วยบัญชี A ตรวจข้อมูล → ดาวน์โหลด/คืนค่า และตรวจจำนวนกับบันทึก
5. ทดสอบบัญชี B ต้องไม่เห็นข้อมูลของ A ห้ามใช้ service-role key ในเบราว์เซอร์

การรัน SQL นี้ยังไม่ได้ทำกับ Supabase จริงจากสภาพแวดล้อมพัฒนา มีการทดสอบ migration และสิทธิ์แยกผู้ใช้ในฐานข้อมูลทดสอบแล้ว รายละเอียดที่ [`CLOUD_BACKUP.md`](CLOUD_BACKUP.md)

## ค่า AI และการตั้งค่ารอบทดลอง

ค่าปริยาย:

```env
AI_ENABLED=true
AI_GLOBAL_DAILY=50
AI_GUEST_DAILY=10
AI_IP_DAILY=15
WEB_SEARCH_DAILY=50
WEB_SEARCH_CACHE_SECONDS=900
```

- ตัวเลขเป็น **จำนวนคำขอ ไม่ใช่ดอลลาร์** การค้นหนึ่งครั้งมีหลาย model/tool calls และค่าใช้จ่ายขึ้นกับคำตอบ/การค้นจริง
- โควตา global ใช้ร่วมกับการอ่านภาพและถาม AI การค้นเว็บมีเพดานแยกแต่ยังอยู่ใต้ global
- ผู้ทดลอง 20 คน ค้นคนละ 2 ครั้ง = 40 ครั้ง เหลือ global อีก 10 ครั้งสำหรับ AI รูป/คำถาม/ลองใหม่ จึงควรประเมินยอดจริงจากรอบนำร่อง ถ้าจะใช้รูปและถามต่อหลายครั้งต้องวางแผนเพิ่ม ไม่อ้างว่า 50 ครั้งพอทุกแบบ
- หากผู้ทดลองใช้ Wi-Fi เดียวกัน เพดาน IP15 อาจหมดก่อนทุกคนทำเสร็จ ผู้ดูแลเลือกตั้ง `AI_IP_DAILY=50` ในวันทดลองได้โดย global ยังเป็น 50 หรือแบ่งรอบต่างวัน
- จำกัดงาน AI พร้อมกัน 2 คำขอและ burst เดิม 3 ครั้ง/นาทีต่อ IP ให้แบ่งเวลาทดลอง ไม่เริ่ม 20 คนพร้อมกัน
- โควตารีเซ็ต 00:00 UTC = 07:00 ไทย `AI_ENABLED=false` ปิดรับ AI; คลัง คู่มือและแผนยังอ่านได้
- cache แยกตามเซสชัน คำขอเหมือนกันทุกเงื่อนไขจึงใช้ซ้ำ ไม่แชร์ข้อมูลข้ามผู้ใช้ ตั้ง cache เป็น 0 เมื่อต้องการทดสอบเวลาค้นใหม่ทุกครั้ง และบันทึกการตั้งค่านั้นในวิธีวิจัย
- การยกเลิกไม่รับประกันว่าผู้ให้บริการจะไม่คิดส่วนงานที่เริ่มไปแล้ว ตรวจยอด OpenAI Billing จริงเป็นระยะ

## งานที่ต้องอาศัยข้อมูล/บัญชี/การทดลองจริงเพิ่มเติม

- **ผลประเมินจากคนจริง**: ความยินยอม รายชื่อรหัส การทำภารกิจ และการตรวจความถูกต้องของโปรเจกต์กับผู้ทดลอง ผู้ช่วยไม่สร้างผลสำเร็จหรือคะแนนแทนผู้เข้าร่วม
- **ความถูกต้องของคำแนะนำและความปลอดภัยชิ้นงาน**: ตรวจต้นฉบับ สเปก และทดลองทำอย่างเหมาะสม การแนบแหล่งอ้างอิงไม่รับรองว่าทุกประโยคถูกต้อง
- **ราคาหรือสต็อกสินค้าแบบยืนยันได้/บาร์โค้ด**: ต้องเลือกแหล่งข้อมูลหรือ API ที่อนุญาต มีความครอบคลุมและเงื่อนไขค่าใช้จ่าย ไม่ได้ใส่ราคาหรือฐานบาร์โค้ดปลอม
- **ลิงก์เสีย/วิดีโอตรงงาน**: ระบบให้ลิงก์ที่ค้นพบและช่องรายงาน ไม่ได้อ้างว่าดูทุกวิดีโอหรือรับประกันว่าลิงก์จะไม่เปลี่ยน เปิดตรวจตัวอย่างจริงก่อนประเมิน
- **การซิงก์อัตโนมัติ/รวมข้อมูลหลายเครื่อง**: รุ่นนี้ใช้สำรองและคืนค่าแบบเลือกเองเพื่อให้ผู้ใช้ตรวจข้อมูลที่จะถูกแทนที่ การแก้แผนภายนอกพร้อมกันหลายเครื่องยังไม่มี
- **การทดสอบผู้ใช้พร้อมกันจำนวนมาก**: แบบทดสอบอัตโนมัติตรวจขอบเขตโควตา/คำขอซ้อน ไม่ใช่ผล load test ของ Render จริง ยังต้องเลือกจำนวนผู้ใช้และช่วงเวลาทดสอบก่อนปรับความจุหรือเสียเงินเพิ่ม
- **แจ้งเตือนการล่ม/การสำรอง off-site อัตโนมัติ**: มี health endpoint และเครื่องมือสำรองด้านล่าง แต่เจ้าของต้องเลือกบัญชีปลายทางและกำหนดตาราง ยังไม่มีการส่งข้อมูลไปบัญชีอื่นโดยอัตโนมัติ

## ดูแลระบบและสำรองโควตา

ตรวจว่า Render ตั้ง `QUOTA_DB` ไว้ **ใต้ mount path ของ persistent disk จริง** เช่น `/var/data/rebuild-quota.sqlite` เมื่อ disk mount ที่ `/var/data` ชื่อเป็นเพียงตัวอย่าง อย่าเปลี่ยน path โดยไม่สำรอง/ย้ายฐานข้อมูล เพราะการเปิดไฟล์ใหม่จะทำให้เคาน์เตอร์และเซสชันเริ่มใหม่

บน Render Shell หรือเครื่องที่เข้าถึงฐานข้อมูลจริงได้:

```sh
# แสดงสถิติจำนวนคำขอ/ผลลัพธ์/เวลารวม ไม่แสดงข้อความหรือภาพผู้ใช้
node scripts/ai-usage.mjs

# ใช้ QUOTA_DB เดิมจาก environment; ปลายทางต้องเป็นไฟล์ใหม่
node scripts/backup-quota.mjs /var/data/backups/quota-2026-10-21.sqlite
```

คำสั่งสำรองใช้ SQLite online backup และตรวจ integrity รองรับข้อมูลที่ commit ใน WAL อย่าคัดลอกเฉพาะไฟล์ `.sqlite` ของระบบที่กำลังเขียนอยู่ สำเนามี session tokens จึงต้องเก็บเป็นส่วนตัว และสำเนาบน disk เดียวกันยังไม่ใช่การสำรองนอกเครื่อง

การคืนค่า: ทดสอบบนสำเนาแยกก่อน จากนั้นหยุดแอป เก็บสำเนาไฟล์ปัจจุบันและไฟล์ WAL/SHM ของมันไว้ คืนไฟล์ที่ตรวจแล้วไป path เดิมโดยไม่ใช้ WAL/SHM เก่าปน แล้วเริ่มแอปใหม่ ผู้ใช้บางคนอาจต้องรีเฟรชเซสชัน ห้ามทดลองทับฐานข้อมูลจริงระหว่างเก็บข้อมูลวิจัย

หาก release ใหม่มีปัญหา ให้ใช้ Render → Manual Deploy → Deploy a specific commit ไป commit ที่ทดสอบผ่านก่อนหน้า การ deploy โค้ดเก่าไม่ย้อนข้อมูลฐานข้อมูลอัตโนมัติ จึงควรสำรองก่อนการเปลี่ยนแปลงใหญ่

## หลักฐานการทดสอบ

ผลตรวจของ release นี้จะสรุปใน `docs/evidence/improvements/validation.json` เป็นการทดสอบทางเทคนิค ข้อมูลจำลองของ automated tests ไม่ใช่ผลผู้เข้าร่วมวิจัย หลักฐาน live search เก่าที่ `docs/evidence/web-search/` ยังคงเป็นผลของ commit ที่ระบุไว้ในไฟล์นั้น

การลองจริงครั้งแรกของชุดปรับปรุงนี้ (`initial-live-validation.json`) พบว่า AI เพิ่มวัสดุและวิธีถ่วงน้ำหนักที่คู่มือ NASA ไม่ได้ระบุ จึงไม่ถือว่าผ่านความถูกต้องของเนื้อหา ผลนั้นเป็นเหตุให้แยกขั้นถอดข้อมูลกับขั้นจับคู่ดังกล่าว แม้มีลิงก์อ้างอิงก็ยังไม่ใช่หลักฐานว่าข้อความทุกข้อถูกต้อง และการตรวจตัวอย่างเดียวไม่ใช่ค่าความแม่นยำของระบบทั้งหมด
